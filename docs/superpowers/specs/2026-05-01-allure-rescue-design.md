## Section 1. ゴールと境界

### 背景
会計担当者が引継ぎなしで離脱（2026年4月）。**翌月10日 月次締め**を絶対に落とせない緊急状況。矢萩さん（株式会社ORI）が最小工数で月次経理を回せる仕組みが必要。

### ゴール
**矢萩さんが翌月10日までに月次試算表を完成できる状態を作る。**

### 達成条件（Success Criteria）
1. 月次の小口領収書（275件＋末〆）が**シート→TKC FX2へ手入力なし**で取り込める
2. 大型支払（カード・振込）の**勘定科目欄が自動補完**される（要確認のみマーク）
3. 仕入請求書（6社）が**自動でシートに反映**される
4. **7店舗の部門コード**がシート上に乗り、CSVにそのまま出る
5. 翌月10日締切に対し、**矢萩さんの実作業=シートのチェック＋TKC取込ボタン**で完了

### 想定される矢萩さんの月次フロー（Before / After）

| Step | Before（現状） | After（Phase 1完了後） |
|---|---|---|
| 1 | 領収書PDF受領→1件ずつ手転記（4-6h） | OCR自動行追加（**0h**、要確認のみチェック15min） |
| 2 | 大型支払 勘定科目を都度判断（1-2h） | LLM補完→確認のみ（**15min**） |
| 3 | 仕入請求書6社を1件ずつ計上（1h） | OCR自動行追加（**5min**） |
| 4 | シート→TKC手入力（4-6h） | CSV出力→TKC取込（**5min**） |
| 5 | 試算表確認 | 試算表確認（**現状維持**） |

**月次工数: 10-15h → 約 5h** が目安。

### スコープ外（Phase 1ではやらない）
- ❌ **給与計算自動化** → 矢萩さんが既存シート＋TKC給与で回す（Phase 1.5で改善）
- ❌ **サロンボード売上集計自動化** → 弊社内で継続運用
- ❌ **ECゼウス・GMO・休日売上の自動取得** → 提供元から手動受領継続
- ❌ **海旬・Primeへの横展開** → Phase 2/3で別途
- ❌ **電子帳簿保存法準拠の証憑管理基盤の刷新** → 既存運用継続

### 制約（Constraints）
- 既存「美容室：入出金経費管理」シート構造は**極力維持**（運用が回っているので）
- 既存`receipt-ocr/`（株式会社ORI稼働中）を**壊さない**形で流用
- TKC FX2の汎用CSV取込仕様は**Phase 0で要確認**（顧問税理士へ問合せ）
- 7店舗の部門コード一覧は**矢萩さん側で取得**（TKCマスタから）

### 対象組織
- **Allireグループ 7店舗**: Allire ／ FONS ／ IVY ／ ICY ／ NI ／ Fivent ／ duft（2026-04開始）
- **部署コード**: 001:Allure / 002:FONS / 003:IVY / 004:ICY / 005:NI / 006:duft / Fiventは別コード（要確認）
- **使用システム**: TKC **FX2クラウド** ／ TKC給与 ／ サロンボード（リクルート）
- **金融**: みずほ銀行3口座、PayPay、セゾンカード（fintechで自動受信）

### 設計原則

1. **既存運用を壊さない**：シート構造は最小侵襲（**部門列ほか4列追加のみ**）。既存運用が回っている前提
2. **矢萩さんの作業 = チェックのみ**：自動行追加→「要確認」マークだけ目視→TKC=TRUEで完了
3. **OCR/LLM の信頼度低い行は自動で「要確認」フラグ**：誤った仕訳を勝手にTKC送りしない
4. **出口モジュール（C4）は差し替え可能**：CSV取込が動かなければ Playwright RPA に交換できる構造
5. **店舗別按分は既存ルールから学習**：サンレンタオル等の按分実績をシート過去データから学習、新規取引先のみ要確認
6. **海旬・Primeへの横展開を見据える**：C4 CSVエクスポータは TKC FX2／TKCまいスター 両対応設計（共通中間表現）

## Section 3. データモデル

### 3-1. 既存シート「美容室：入出金経費管理」への追加列

**既存（9列）**:
`NO | 領収日 | 支払先 | 勘定科目 | 合計金額 | 使用者 | リンク | TKC | 備考`

**提案（13列、4列追加 ※全部右端に追加で既存数式を壊さない）**:

| 追加列名 | 説明 | 例 |
|---|---|---|
| **部門** | 7店舗の部門コード | `001:Allure` 〜 `006:duft` 等 |
| **税区分** | TKC FX2取込用 | `課仕10%` / `課仕8%軽` / `非課税` / `不課税` |
| **要確認** | LLM/OCR信頼度低い行のフラグ | `TRUE` / `FALSE` |
| **OCR信頼度** | デバッグ用（後で削除可） | `0.92` 等 |

**運用ルール**:
- 自動追加された行は **TKC=FALSE、要確認=TRUE/FALSE**（信頼度依存）
- 矢萩さんは **要確認=TRUE のものだけチェック** → 修正後に TKC=TRUE
- 要確認=FALSE のものは目視スキップしてOK（信頼してCSV出力対象）

### 3-4. データ整合性ルール

| ルール | 内容 |
|---|---|
| 部門必須 | 全行に部門コードが入っていないとCSV出力不可（要確認フラグ立て） |
| 勘定科目必須 | 空欄の行はCSV出力不可（自動でLLM補完→要確認） |
| 按分行は等しい証憑リンク | 1枚の請求書から複数行に分かれる場合、リンク列は同じファイル名を使う（既存運用と同じ） |
| 金額符号 | マイナス（赤伝）は別途扱い（既存運用の「-1,228,170」等を踏襲） |
| TKC=TRUE は変更不可 | 一度TKCに取り込んだ行は編集禁止（誤再取込防止） |

### 4-3. 矢萩さんの「要確認」UI

シートの **要確認=TRUE 行** に対して以下のいずれかが付く：

| マーク | 意味 | 矢萩さんの対応 |
|---|---|---|
| 🔍 OCR低信頼 | 金額/日付/支払先がOCR読取に自信なし | 該当リンクのPDFを開いて目視確認、修正 |
| ❓ 部門不明 | 使用者→部門マッピングに該当なし（新人入社等） | `_使用者マスタ` に1行追加 |
| ❓ 科目不明 | 支払先が `_科目マスタ` に未登録 | 勘定科目を判定し、必要なら `_科目マスタ` に追加 |
| ⚠ 按分要 | サンレンタオル等、按分対象だが配分不明 | 過去パターンを参照 or 戸田社長に確認 |
| ⚠ 大型支払 | カード明細・通帳の項目で勘定科目LLM補完したが信頼度低 | 内訳確認、勘定科目修正 |

各マークの「修正方法」が同じセル列のコメントに表示されるので、矢萩さんは指示通り対応すれば済む。

### 4-4. 失敗時のフォールバック

| 失敗パターン | フォールバック |
|---|---|
| OCRが完全失敗（PDF壊れ等） | 該当行は作らない、`_OCR失敗ログ` シートに記録、Gmail通知 |
| Drive APIエラー | リトライ3回 → 失敗ログ＋Gmail通知 |
| TKC CSV取込失敗 | 該当行は TKC=FALSE のまま、矢萩さんが手入力でカバー |
| 顧問税理士のCSV仕様提供が遅延 | C4 を未稼働のまま、シート整備（C1〜C3）だけ先行運用 |
| LLM分類が偏る／間違える | 過去275行のラベル付き実績を「正解データ」として `_科目マスタ` に蓄積 |

## Section 5. エラー処理・テスト戦略

### 5-1. 失敗モード一覧と対応

| # | 失敗モード | 検知方法 | 自動対応 | 通知 |
|---|---|---|---|---|
| F1 | OCR読取不能（破損PDF） | OCR API がエラー | 該当ファイルを `_OCR失敗` フォルダへ移動、ログ記録 | Gmail（即時） |
| F2 | OCR部分失敗（金額のみ読めない等） | 必須フィールド null | 行作成、要確認=TRUE、欠損列ハイライト | 日次サマリ |
| F3 | 使用者抽出失敗 | ファイル名から抽出できない | 「使用者=不明」で行作成、要確認=TRUE | 日次サマリ |
| F4 | 部門推定失敗 | `_使用者マスタ` に該当なし | 部門=空、要確認=TRUE、原因をマーク | 日次サマリ |
| F5 | 勘定科目推定失敗 | `_科目マスタ` に支払先未登録 | 勘定科目=LLM補完、信頼度<0.8 → 要確認=TRUE | 日次サマリ |
| F6 | 按分判定失敗 | 過去実績から配分が読めない | 1行のまま投入、要確認=TRUE、コメントで「按分要」 | 日次サマリ |
| F7 | 大型支払LLM補完の信頼度低 | confidence < 0.7 | 行作成、要確認=TRUE | 月初サマリ |
| F8 | 重複行検知 | 既存行と日付/金額/支払先一致 | 新行作成しない、`_重複ログ` に記録 | 日次サマリ |
| F9 | TKC CSV出力エラー（必須欄空） | C4 のバリデーション | CSV出力中断、欠損行リストをシートに表示 | 即時 |
| F10 | TKC取込時のエラー | TKC側のエラーメッセージ | 矢萩さんが該当行を要確認に戻す（手作業） | — |
| F11 | Drive API レート制限 | 429エラー | 指数バックオフ＋リトライ3回 → 失敗ログ | 月次1回サマリ |
| F12 | LLM API障害 | リクエストタイムアウト | リトライ3回 → 該当行は「LLM保留」ステータス、翌日再実行 | 月次1回サマリ |
| F13 | OCR API キー失効 | 401エラー | 即時通知＋全処理停止 | Gmail（最高優先） |

### 5-2. テスト戦略

#### Phase 1テスト計画

| Stage | 内容 | 合格基準 |
|---|---|---|
| **T1: 単体テスト** | 各コンポーネント（C1〜C5）の関数レベル | カバレッジ70%以上、主要パスは100% |
| **T2: バックテスト（過去データ）** | 過去275行のシートをラベル付き正解として、OCR→分類精度を測定 | 勘定科目判定 95%以上、部門判定 98%以上 |
| **T3: 並走テスト（3月実データ）** | 3月の領収書PDFをシステムに通し、矢萩さん手入力結果と比較 | 差分件数 5%以下、致命的誤りゼロ |
| **T4: 並走テスト（4月実データ）** | 4月分でも同じ並走 | T3と同水準を維持 |
| **T5: E2Eテスト（5月実データ）** | 5月をシステム正本で運用、翌月10日に試算表完成 | 翌月10日締切達成 |
| **T6: TKC取込実機テスト** | C4出力CSVをTKC FX2に実取込 | エラーゼロ、勘定科目・部門・税区分が正しく取込まれる |

#### バックテストの具体手順

1. 既存「美容室：入出金経費管理」シートの過去275行を**正解データ**として抽出
2. 同行に紐づくPDFを Drive から逆引き
3. C1（OCR + 部門推定 + 勘定科目推定）に通す
4. 出力 vs 正解の差分集計（完全一致率／勘定科目誤分類混同行列／部門誤推定／金額誤読率）
5. 3%以上の誤分類が出る支払先パターンは `_科目マスタ` に追加してリトライ

#### 並走テストの具体手順

1. C1〜C5を実運用に投入、ただし TKC=TRUE への自動更新は止める
2. 矢萩さんは並行で従来通り手入力（シートに別タブで「人手版」を残す）
3. 月末に**自動版 vs 人手版** の行単位差分を集計
4. 差分が5%以下なら次月から**自動版を正本**に切替

### 5-3. ロギング設計

| ログ種別 | 保存先 | 保存期間 |
|---|---|---|
| OCR成功・失敗 | `_OCRログ` シート | 6ヶ月 |
