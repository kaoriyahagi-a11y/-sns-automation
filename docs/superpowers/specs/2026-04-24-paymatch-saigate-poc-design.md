## 1. 背景と目的

### 1.1 背景

矢萩は経理代行11社の支払業務を運用しているが、現状の手順は：

1. クライアントから請求書がLINE等で届く（SAIGATEは毎月ZIPで40〜70枚の会計資料）
2. Google Sheetsの「入出金管理表」に手入力
3. みずほビジネスWEBで振込予約（下書き作成）
4. 下書き確定 → 振込実行

この流れで**毎月1件程度、何らかの転記ミス**が発生している（金額・振込先・期日・入力漏れ・件数ズレ）。

### 1.2 目的

- **「下書きの時点で間違いを検知」**できる突合ツールを最短で実装する
- SAIGATE（月1 ZIPバッチ）で PoC → 精度確認後に他10社へ横展開
- 親プロジェクト UoBO の `InboxHub / LedgerGen` の先行プロトタイプを兼ねる

### 1.3 成功条件

- 3ヶ月連続で**誤検知ゼロ**（false negative なし）
- 香織さんが「手作業より速い」と実感
- SAIGATE以外の1〜2社に横展開できる汎用性

### 1.4 スコープ

**含む**:
- ZIP展開、書類種別判定、請求書のみ抽出
- 請求書OCR（取引先・金額・期日・摘要・振込先）
- Google Sheets 月別タブへの自動行追加
- 突合①：請求書PDF vs スプシ入力
- 突合②：スプシ vs みずほ下書きスクショ（OCR）

**含まない（Phase 2 以降）**:
- 入金側（通帳 vs 入金予定）の突合
- LINE Bot での自動受信（PoCは手動ZIP配置）
- SAIGATE以外のクライアントへの横展開
- 振込実行の自動化（原則：人間が必ず最終クリック）
- 発注書・納品書の管理

## 3. 全体アーキテクチャ

### 3.1 コンポーネント構成（5モジュール）

```
sns-automation/paymatch/
├── zip_ingester.py     # ZIP展開 → 書類種別判定
├── invoice_ocr.py      # 請求書PDF → Claude Vision → JSON
├── sheets_writer.py    # Google Sheets 月別タブに行追加
├── reconciler_pre.py   # 突合①：ZIP請求書 vs スプシ
├── reconciler_post.py  # 突合②：スプシ vs みずほ下書きスクショ
└── cli.py              # コマンドライン実行エントリ
```

### 3.2 モジュール責務

#### ① zip_ingester.py（書類受取・仕分け）

**責務**: ZIPを展開し、中身の各PDFを書類種別で分類、請求書だけを下流に渡す。

**入力**: `C:\Users\orika\paymatch\inbox\YYYY-MM-DD_SAIGATE.zip`

**処理**:
1. ZIP展開 → `paymatch/tmp/YYYYMMDD/`
2. 各PDFをClaude Visionで書類種別判定（請求書/発注書/納品書/その他）
3. 請求書のみ `paymatch/invoices/YYYY-MM/` に移動
4. 判定結果を `ingest_log.json` に記録

**出力**: `paymatch/invoices/YYYY-MM/*.pdf`（請求書のみ）

---

#### ② invoice_ocr.py（請求書OCRエンジン）

**責務**: 請求書PDFから構造化データを抽出。

**入力**: `paymatch/invoices/YYYY-MM/*.pdf`

**抽出項目**:
- 取引先名（発行元）
- 請求日
- 支払期日
- 金額（税込）
- 摘要（件名 or 初行）
- 振込先（銀行・支店・口座種別・口座番号・名義）
- OCR確信度（high / medium / low）

**出力**: `paymatch/out/invoices_YYYYMMDD.json`

**技術スタック**: Claude API (claude-opus-4-7) with Vision、日本語請求書プロンプトチューニング。

---

#### ③ sheets_writer.py（スプシ書き込み）

**責務**: OCR結果を既存の「入出金管理表」月別タブに追加。

**既存スプシ列構成**:
```
振込日 | 取引先名 | 金額 | 摘要 | ステータス | 支払口座 | 支払確認済 | 確認済み合計 | 合計金額
```

**処理**:
1. 該当月タブ（例：`2026年4月(振込)`）を特定・なければ作成
2. 新規行を追加（既存行の上書きはしない）
3. 振込先口座情報は**列にない**ため、別タブ `_invoice_raw` に生データを残す
4. OCR確信度が low の行は **黄色ハイライト**

**技術スタック**: Google Sheets API v4、既存GCP SAキー流用。

---

#### ④ reconciler_pre.py（突合①：請求書 vs スプシ）

**責務**: ZIP内の請求書とスプシ追加行が一致するか検証。

**チェック項目**:
| 項目 | ルール |
|---|---|
| 件数 | ZIP内請求書数 == スプシ新規追加行数 |
| 金額 | 請求書金額 == スプシ金額（**1円ズレもNG**） |
| 期日 | 請求書の支払期日 ≥ スプシ振込日、かつ差分 ≤ 7日 |
| 重複 | 同一取引先 × 同一金額 × 同一請求日 が別タブに既存でないか |

**出力**: `paymatch/out/reconcile_pre_YYYYMMDD.md`

---

#### ⑤ reconciler_post.py（突合②：スプシ vs みずほ下書き）

**責務**: 香織さんがみずほで作成した下書き画面スクショをOCRし、スプシと突合。

**入力**:
- スプシの該当月タブ
- `C:\Users\orika\paymatch\mizuho\YYYY-MM-DD_draft_*.png`（複数ページ対応）

**OCR抽出項目**:
- 振込日
- 振込先銀行・支店
- 口座種別・口座番号
- 受取人名義
- 金額

**チェック項目**:
| 項目 | ルール |
|---|---|
| 件数 | スプシ支払行数 == みずほ予約件数 |
| 金額 | 各行の金額完全一致 |
| 振込日 | スプシ振込日 == みずほ振込指定日 |
| 取引先マッチング | スプシ取引先名 vs みずほ受取人名義（Claude API fuzzy match） |
| 漏れ | スプシにあってみずほにない／逆パターン |

**出力**: `paymatch/out/reconcile_post_YYYYMMDD.md`

## 4. エラー処理・例外ケース

### 4.1 OCR失敗・低確信度

| 状況 | 対処 |
|---|---|
| 金額を読み取れない | `null` として出力 → レポートに **❌ 要手入力** 明示 → 他の請求書は続行 |
| 確信度 low | `confidence: low` → レポートに **⚠️ 要確認** |
| 書類種別が曖昧（請求書兼納品書等） | 両方のフォルダにコピー → 「種別曖昧」と明記 |

**原則**: **止めるより進める**。エラー分だけ人手補正。

### 4.2 突合の判定基準

| 項目 | 判定 |
|---|---|
| 金額 | 完全一致のみOK（1円ズレも NG：消費税計算ミス検知） |
| 振込日 vs 支払期日 | 振込日 ≤ 支払期日 かつ 差分 ≤ 7日 → OK |
| 取引先名 | Claude API類似度判定（「（株）○○」「○○株式会社」「○○（カ」は同一） |
| 重複 | 同一取引先 × 同一金額 × 同一請求日 が別タブに既存 |

### 4.3 例外パターン

| ケース | 対応 |
|---|---|
| 分納請求（支払期日が複数） | OCR時に複数行抽出 → 1請求書→複数スプシ行にマッピング |
| 振込先変更通知 | OCR時にキーワード検知 → **🔔 口座変更の可能性** 警告 |
| 前月分混入 | 請求月 vs 処理対象月を比較 → 警告のみ |
| みずほ下書き複数ページ | スクショを複数枚受付 → OCR結果を連結 |
| ZIP内に一覧表Excel | 参考情報として読む（優先度は請求書本体） |

### 4.4 システム系エラー

| エラー | 対応 |
|---|---|
| Google Sheets API失敗 | ローカルCSVに出力 → 後で手動貼付 |
| Claude API失敗 | 3回リトライ → 該当PDFスキップしてレポートに記載 |
| ZIP破損 | エラーログ記録 → 終了コード1で停止 |

### 4.5 安全ガード

- 振込実行の自動化はしない（必ず人間が最終クリック）
- スプシの既存行上書きはしない（新規追加のみ）
- 突合レポートが❌を含む場合は `approval_needed: true` をレポート先頭に明示

## 5. テスト方針

### 5.1 単体テスト（pytest）

| モジュール | テスト対象 |
|---|---|
| `zip_ingester` | 書類種別判定精度 ≥ 95% |
| `invoice_ocr` | サンプル請求書10枚で金額・取引先・期日の抽出一致率 ≥ 90% |
| `sheets_writer` | モックSheetsAPIで列順・フォーマット検証 |
| `reconciler_pre` | 意図的ズレデータで❌検知確認 |
| `reconciler_post` | スクショサンプルで件数・金額突合ロジック確認 |

**テストデータ**: SAIGATE過去ZIPから匿名化した3ヶ月分を `tests/fixtures/` に配置。

### 5.2 統合テスト（手動シナリオ）

```
[1] ZIP配置 → cli.py ingest → 突合①レポート確認
[2] 意図的にスプシ1行編集（金額変更）→ cli.py reconcile-pre → NG検出
[3] みずほ下書きスクショ配置 → cli.py reconcile-post → OK
[4] 意図的にスクショ1件抜く → reconcile-post → 件数ズレNG検出
```

### 5.3 実運用PoC

**初回**：今月のSAIGATE ZIPで並行運用（従来手作業とシステムを両方実行し比較）

**2回目〜3回目**：週次で見直し、精度 ≥ 95% 確認

**PoC卒業基準**:
- 3ヶ月連続で誤検知ゼロ
- 香織さんが「手作業より速い」と実感
- 横展開可能な汎用性確認

### 5.4 回帰テスト

- 過去のZIP × 過去のみずほスクショ → 突合結果が不変であることを確認
- OCRプロンプト変更時は全fixtureで再実行

## 9. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| OCR精度不足（40-70枚中の請求書判定が揺れる） | 請求書取りこぼし | 確信度low を全て手レビュー／判定プロンプト継続改善 |
| みずほ下書き画面の仕様変更 | 突合②失敗 | スクショ形式をバージョン管理／OCRプロンプトに複数フォーマット対応 |
| 既存スプシの列順が変わる | 書き込み失敗 | スプシ1行目のヘッダ名で列位置を動的解決 |
| Claude API料金肥大 | コスト増 | OCR結果キャッシュ／低解像度プリプロセス |
| 香織さんが途中でみずほ下書きを誤修正 | 突合②がズレる | 突合実行前に「スクショは最終版ですか？」確認プロンプト |
